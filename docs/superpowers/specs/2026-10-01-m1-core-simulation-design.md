## 1. Scope

**In:** a pure TypeScript package `@wordfarer/core` holding every rule that moves a number, plus the pacing bots that play it.

- Encounters, Understanding, the manual **Listen** action, bulk buy, milestones.
- Words: pick-up, tags, ranks, the retrievability-weighted bonus and its floor.
- FSRS review: the 10-item queue, Insight, practice mode.
- Insight upgrades and Passport Stamp upgrades.
- Journeys and culture cards: slots, durations, seeded draws with repeats, a repeat's reward, set bonuses, seasonal in-season bonus.
- Set Sail: goals, stamps, 3 regions × 4 destinations, destination order, the Mudik finale gate, and Mastery mode with scaling goals.
- Grammar nodes and Pemandu automation.
- The offline cap (24 h, upgradable to 72 h) and clock clamping (DN21).
- The unfold state: which tabs and features are revealed (DN7), as data for the UI.
- The typed event log and a state hash, ready for ranked replay (M5).

**Out:** UI, saves and migrations (M4), the Worker replay endpoint (M5), real content (M2), achievements and Immersion's label mapping (no number moves; `core` only exposes the set of Mastered item IDs), entitlements (a `Platform` concern; `core` takes the set of playable regions as input).

## 2. Research and decisions

All figures below were measured on 2026-10-01 on the operator's laptop, under Node 24 (V8) and macOS JavaScriptCore (the engine in Safari and on every iPhone). The probe scripts are kept in the git-ignored `.superpowers/sdd/m1/research/`; the guarantees they establish are re-asserted by tests in M1 itself (§7), so the scripts are not load-bearing.

### 2.1 Arithmetic must be identical on every engine

ECMAScript leaves `Math.pow`, `exp`, `log` and `**` implementation-approximated. Only `+ − × ÷` and `sqrt` are correctly rounded everywhere. Ranked verification (§10.2 of the parent) replays an iPhone's events on Cloudflare's V8, so any difference can flip a purchase and diverge the replay.

| Operation, same inputs on both engines           | Results whose bits differ |
| ------------------------------------------------ | ------------------------- |
| `Math.pow(1.15, n)`, integer `n` (cost)          | 49,204 / 100,000          |
| `Math.exp`                                       | 9,854 / 100,000           |
| `Math.log`                                       | 877 / 100,000             |
| `Math.pow(10, n)`, integer `n`                   | 15,744 / 50,000           |
| `break_infinity` `Decimal.pow(1.15, n)`          | 49,204 / 100,000          |
| `break_infinity` add, sub, mul, div              | 0 / 50,000 each           |
| `Math.expm1`                                     | 18,535 / 200,000          |
| `Math.log1p`                                     | 4,037 / 200,000           |
| `@stdlib` pure-JS `pow` (3 input shapes)         | 0 / 2,000,000 each        |
| `@stdlib` `exp`, `ln`, `log10`, `expm1`, `log1p` | 0 / 200,000 each          |
| `ts-fsrs` `forgetting_curve`                     | 0 / 2,000,000             |
| `ts-fsrs` scheduler (3,000 cards × 25)           | 0 / 75,000 states         |

**Decision D-M1-1.** Every transcendental function in `core` goes through one module, `det-math.ts`, built on the `@stdlib/math-base-special-*` pure-JS ports (Apache-2.0, compatible with our licence; their licence text joins the third-party notices of every shipped build). An ESLint rule bans `Math.pow`, `Math.exp`, `Math.expm1`, `Math.log`, `Math.log1p`, `Math.log10`, `Math.log2`, `Math.cbrt`, `Math.hypot`, the trigonometric functions and the `**` operator in `packages/core/src`, and `Decimal.pow`, `Decimal.exp`, `Decimal.log*` and their instance forms. `Num` (break_infinity) is used only for its measured-safe arithmetic, and powers are built as `Decimal.fromMantissaExponent` from a `det-math` base-10 logarithm. Its normalisation is not used: break_infinity normalises with `Math.floor(Math.log10(|m|))`, and its `add` leaves the mantissa below 1 for the integer mantissas 999999999999999 and 999999999999998 on V8 and JavaScriptCore alike (measured 2026-10-01 in #26; the two engines agreed on all 2,527 boundary floors tried), so one value could be stored as two tuples. `Num` brings every result back to `1 ≤ |m| < 10` with comparisons alone, and `Num.from` takes its exponent from `det-math`. `ts-fsrs` stays (the parent spec's choice): its 8-decimal rounding absorbs the engine differences.

### 2.2 Integration: anchored state, integer clock, hourly rate buckets

Four variants were tried against a toy economy (50 and 450 words with mixed stabilities, automation buying on a fixed grid):

| Method                                                                          | `advance(a)+advance(b)` vs `advance(a+b)`                              | 24 h offline, 450 words, 1 s automation |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | --------------------------------------- |
| Exact continuous integral, integrating from wherever the last call stopped      | 1,359 / 20,000 not bit-identical                                       | 12 s (138 µs per evaluation)            |
| Same, but state held at its last event (an **anchor**), time as float days      | 1 / 2,000 (a tick revisited through float rounding: a double purchase) | same per-evaluation cost as row 1       |
| Anchor, **integer-millisecond** clock                                           | 0 / 20,000                                                             | same per-evaluation cost as row 1       |
| Anchor, integer clock, **hourly buckets** with each word's exact mean R (below) | 0 / 3,000                                                              | 9 ms (101 buys); 58 ms (86,400 buys)    |

**Decision D-M1-2: the time model.**

1. **Integer milliseconds.** All simulated time is an integer count of milliseconds (`SimMs`, a branded number, always a safe integer). There are no fractional days anywhere in state.
2. **Anchored state.** The stored state holds every quantity at its **anchor**: the time of the last event or internal event. Values at "now" are derived (`view(state, wallMs)`) and never stored. Splitting an interval therefore cannot change any stored arithmetic, which is what makes associativity exact rather than approximate.
3. **Hourly rate buckets.** Production inside one clock hour (`[h·3,600,000, (h+1)·3,600,000)` on the simulated clock) is constant. Each word's bonus in that bucket uses the word's **exact mean retrievability over the bucket**, computed in closed form from the FSRS-6 curve, so while Encounter counts are unchanged a whole hour's total equals the continuous model's. A review, or a return the offline cap clips, restarts every word's mean from that moment, since the state holds one `memorySince` (#28). A pick-up restarts nothing: the new word has R = 0, so its bonus is its floor whatever the window. A purchase changes only the Encounter factor of the rate, so the bucket's per-word means are reused and a purchase costs O(Encounters), not O(words).
4. **Closed-form mean R.** FSRS-6 gives `R(t) = (1 + F·t/S)^(−d)` with `d = 0.1542` and `F = 0.9^(−1/d) − 1`. Its integral is `∫₀ᵀ R = (S / (F·(1−d))) · expm1((1−d) · log1p(F·T/S))`. The textbook form `((1+x)^(1−d) − 1)` loses precision on short gaps (worst relative error 9.0e-6 at `T` = 1e-9 d, `S` = 365 d, against a 60-digit reference); the `expm1`/`log1p` form's worst is 1.3e-15. A window starting `a` days after the review is the same curve shifted: `mean(S, a, T) = R(S, a) · mean₀(S + F·a, T)`. Taking the difference of two integrals instead loses up to 0.58% (measured at `a` = 100 years, `T` = 1 ms); the shifted form's worst row against the 30-digit reference table is 1.19e-15 (#28).
5. **Internal events fall on the absolute clock.** Automation ticks fall on a fixed grid of the simulated clock, and journey returns at fixed times on the same clock. When the next purchase becomes affordable, its tick is solved in O(1) from the bucket's linear rate, then confirmed by evaluating the tick and the one before it, so the result never depends on how far `advance` was asked to go.

The parent's wording "closed-form integration between events" still holds: each bucket is integrated in closed form.

### 2.3 Wall clock and simulated clock

`core` keeps two clocks. `sim` (integer ms) drives the economy: production, journeys, automation and buckets. `wall` (integer ms, the latest wall-clock time seen) drives **memory and the calendar**: FSRS due times, retrievability and ranks, and seasonal festivals. Forgetting happens in real time, so a month away must age every word by a month even though the economy only credits the offline cap.

`advance(state, wallMs)` computes `elapsed = clamp(wallMs − state.wall, 0, offlineCap)`, adds it to `sim`, and sets `wall = max(state.wall, wallMs)`. A backwards jump advances nothing and a forward jump is capped (parent §10.3). The difference `skew = wall − sim` changes only at such a clamp, which is an anchor, so inside a bucket a word's retrievability is evaluated at wall time `t + skew` and the closed form of §2.2 still applies. The pure, uncapped primitive is `integrate(state, elapsedMs)`, which moves both clocks by the same amount; the associativity property is stated over it.

The pacing bots start their wall clock at **2027-01-04 00:00 UTC**, so festival windows fall on the same simulated days in every run.

## 3. Package shape

```
packages/core/src
  num.ts           Num type over break_infinity: arithmetic only, powers via det-math
  det-math.ts      pow, exp, ln, log10, expm1, log1p over @stdlib; nothing else in core calls Math.* transcendentals
  clock.ts         SimMs brand, buckets, grids, clamp
  rng.ts           seeded PRNG (xoshiro128**, four 32-bit integers of state, serialisable)
  balance.ts       every tunable number, one table (parent §3)
  course.ts        CourseData: the typed shape content must produce (M2's Zod schema targets it)
  state.ts         GameState, the anchor, initial state
  events.ts        the GameEvent union and its validator
  encounters.ts    costs, bulk buy, milestones, base rates
  words.ts         pick-up, tags, rank bonus, floor, per-encounter word multiplier
  memory.ts        ts-fsrs wrapper, ranks from stability, queue, Insight, practice
  production.ts    bucket rates and the closed-form mean R
  upgrades.ts      Insight and stamp upgrade catalogues and effects
  journeys.ts      slots, durations, seeded card order, sets, seasons
  sail.ts          goals, stamp gain, destination order, finale, Mastery mode
  grammar.ts       nodes and their multipliers
  automation.ts    Pemandu: best-payback choice and its grid
  unfold.ts        which features are revealed (DN7), from state alone
  sim.ts           integrate, advance, view
  log.ts           apply(event) and replay (#34): sail and journeys import sim, so these sit above it
  hash.ts          the canonical serialisation and stateHash (#34)
  index.ts         the public API
packages/core/test   unit, property and determinism tests
packages/core/fixtures/synthetic-course.ts   the generated course the bots play
packages/bots        personas, the open scheduler, the pacing report, and the CI assertions
```

`core` has no dependency on DOM, timers, network or the system clock. An ESLint rule enforces this: `Date.now`, a zero-argument `new Date()`, `setTimeout`, `setInterval`, `fetch`, `window`, `document`, `performance`, `crypto` and `Math.random` are banned. `memory.ts` may build `new Date(wallMs)` from an explicit argument, because `ts-fsrs` takes `Date` objects; that reads no clock. `ts-fsrs` is driven with `Good` for a correct answer and `Again` for a wrong one, with fuzz off so scheduling is deterministic.

## 4. Events, state and API

- **Events** (all carry `wallMs` and a sequence number `seq`; `apply` first advances to `wallMs`, so an earlier `wallMs` is clamped exactly as §2.3 clamps a backwards clock, never rejected): `listen`, `buyEncounter {id, count}`, `pickUpWord`, `answerReview {itemId, correct, latencyMs, promptType}`, `answerPractice {itemId}`, `buyUpgrade {id}`, `startJourney {slot, durationId}`, `collectJourney {slot}`, `setSail {to?}`, `buyGrammarNode {id}`, `setAutomation {enabled, intervalMs}`. A review answer carries its latency for the bot signals (parent §10.4).
- **API:** `initialState(wallMs)`, `apply(course, state, event) → Result<GameState, Rejection>`, `advance(course, state, wallMs) → {state, summary}` (the summary feeds the "welcome back" card: time credited, whether the cap clipped it, Understanding earned, journeys returned), `integrate(state, elapsedMs)`, `view(course, state, wallMs)` (derived numbers, the review queue, rates with their multiplier breakdown for DN6, the unfold flags), and `stateHash(state)` (SHA-256 of a canonical serialisation, for the replay check in M5, computed synchronously with the pure-JS `@noble/hashes` (MIT), since WebCrypto is asynchronous and a global). Amended in #27: a function that reads course data takes the course first, because state holds no content (a save stays small, and a replay supplies the course it ran against); `initialState` gains a seed with the first story that draws from the RNG (#30). The Encounter actions `apply` dispatches, `listen(course, state)` and `buyEncounter(course, state, id, count) → Result`, act at the state's own simulated time; `apply` (#36) advances to the event's `wallMs` and checks `seq` first. Amended in #29: `view` also returns `breakdown`, each owned Encounter's rate as the product of named lines (`encounters`, `milestones`, `words`, one `phrasebook:<tag>` per owned Phrasebook of its tags, then `stamps`), and `rate` is the sum of those rates, so the rate shown is the rate paid; `buyUpgrade(course, state, id) → Result` acts at the state's own simulated time, like the Encounter actions. Amended in #30: `initialState(wallMs, seed)` seeds the state's own streams (`cards` so far); `startJourney(course, state, slot, durationId)` and `collectJourney(course, state, slot) → Result` act at the state's own simulated time; the `advance` summary gains `journeysReturned`. Amended in #31: `initialState(wallMs, seed, playableRegions = 3)`; `setSail(course, state, to?) → Result` acts at the state's own simulated time, and `to` names the destination to replay from the finale sail on; `view` also returns `sail` (the goal, the progress towards it, and exactly what a sail resets, keeps and pays, DN3) and `unfold` (parent §4.1's reveal flags); `understandingNow` moves to `production.ts`; the route (`route`, `currentDestination`, `currentRegion`, `regionsReached`) is public. Amended in #32: state gains `grammar`, the owned node ids in the order bought, which a sail keeps; `buyGrammarNode(course, state, id) → Result` acts at the state's own simulated time; `pickUpPool(destination, held, nodes)` takes the owned nodes too; the breakdown gains a `grammar` line after `words`; `view`'s `sail.keeps` gains `grammarNodes`. Amended in #33: `integrate(course, state, elapsedMs)` takes the course, since with Pemandu on it buys; state gains `automation` (`{enabled, intervalMs}`, off at 10 s to start), which a sail keeps; `setAutomation(course, state, enabled, intervalMs) → Result` acts at the state's own simulated time and banks production first; `advance`'s `understandingEarned` is what was produced, so Understanding Pemandu spent in the credited time is added back; `automationOpensAt`, `automationUnlocked`, `bestPayback`, `nextPurchaseTick` (the tick and the Understanding held there), `rateGain` and `encounterPrice` (the one price a purchase by hand and one by Pemandu pay) are public. Amended in #34: the union gains `resume`, which the client records whenever the game opens; it changes nothing but banks the elapsed time, capped as `advance` caps it, so a visit with no other action still counts and the welcome-back card shows only what was banked (operator, 2026-10-03). `promptType` is one of `choice`, `typed` and `tiles`, parent §3.4's three prompt types. `parseEvent(input)` turns untrusted input (a stored log, a request body) into a `GameEvent` or a typed `EventError`, checked in this order: not a plain object, an unknown `type`, then each field of that type in its listed order (missing, of the wrong type, not a safe integer, out of range), then any field the type does not have, in code-unit order. `seq` is at least 1; `wallMs`, `latencyMs` and `slot` at least 0; `count` and `intervalMs` at least 1; an optional field (`setSail`'s `to`) is absent or of its type. State gains `seq`, the last accepted event's, 0 to start. `apply` checks `seq` first and refuses one not above the state's as `staleSeq`; gaps are allowed, since a refused event keeps its number. It then advances to `wallMs` and dispatches. A refusal returns no state, and the caller keeps the state it passed, unadvanced, so a refused event is as if it was never sent. The live state changes only through `apply`: `advance`'s result feeds `view` and the welcome-back card and is never stored, since advancing and then applying differs from applying alone whenever the cap clips (§7). `replay(course, state, events)` applies a log in order and returns the final state with each refusal and its `seq`. `stateHash` lives in `hash.ts`: SHA-256 over a canonical serialisation in which object keys are sorted in code-unit order and every number is written as the 16 hex digits of its IEEE-754 bits, because ECMAScript leaves the last digit of `Number.prototype.toString` to the engine and the bits are what must agree; `-0` and `0` therefore hash apart. A value that is not plain data (a `Num` or other class instance, `undefined`, a non-finite number, a function) throws, so it can never hash as something else.
- **Rejections are values, not throws.** An unaffordable purchase, an unknown Encounter, a count that is not a positive integer, a scored review of an item that is not due, or a `seq` that does not increase returns a typed `Rejection` and leaves state unchanged; so does an unknown upgrade, one already at its last level, one whose prerequisite is not owned, or one the player cannot pay for, checked in that order (#29). So does an Encounter from a region not yet reached (#31), and a Set Sail on a course with no destination there, without a destination named when one must be, naming an unknown destination or one that is not next, into a region outside the playable ones, or before the goal is met, checked in that order (#31). So does a grammar node the course does not have, one already owned, one not yet available, or one the player cannot pay for, checked in that order (#32). So does a `setAutomation` before Pemandu opens, or at an interval the player does not own, checked in that order and whether it turns Pemandu on or off (#33). M5's replay flags are exactly these rejections.
- **State is plain, serialisable data:** no classes, no `Num` instances inside state (stored as `[mantissa, exponent]` tuples), so a save is `JSON.stringify` and the hash is stable.

## 5. Game rules this design fixes

The parent leaves these open. They are **starting values for the bots to tune**, recorded in `balance.ts`, and the operator may veto any of them.

- **Listen:** +1 💬 per tap, no upgrades. How much it can matter is bounded by §6 assertion 7 (DN10).
- **Insight upgrades:** journey slot 2 and 3; offline cap +24 h (twice, to 72 h); "Phrasebook" ×2 production for one tag (one per tag; an Encounter with two owned Phrasebooks' tags gets both); faster Pemandu interval (5 s, 2 s, 1 s). An upgrade that unlocks a distinct thing (slot 3, each Pemandu tier) is its own upgrade and requires the one before it; one that adds the same step again (the offline cap) is one upgrade with levels. Each level's cost is in `balance.ts` (#29).
- **Stamp upgrades** (bought with 🛂, kept forever): starting Understanding; Encounter cost −5% per level (capped at −40%); journey duration −10% per level (capped at −30%); Pemandu unlocked one destination early. Each level of starting Understanding gives 100. Each stamp **ever earned** also gives +10% global production (parent §3.1), so spending stamps on upgrades never lowers it (operator, 2026-10-02, #29); state keeps the stamps held and the total earned apart.
- **Pick-up:** the next word of the current destination, in curriculum order (CEFR, then course order), costs `20 · 1.15^n` Understanding, `n` being the items of that destination already picked up (#28).
- **Grammar:** each node multiplies every word whose lexicon `root` it attaches to by `×(1 + g)`, with `g = 0.5` to start, and adds the derived words to the pick-up pool. Decided in #32: grammar opens at region 2, and a node is available once its own region is reached, as Encounters are; the next node costs `50 · 1.5^n` Insight, `n` being the nodes already owned, so the order is the player's; two owned nodes on one root compound, `×(1 + g)²`, since each node multiplies; the derived words of the owned nodes join the pool after the card packs, in course order, so the pool never depends on purchase order. The breakdown's `grammar` line is `(1 + Σ b_w·f_w) / (1 + Σ b_w)` over the words sharing a tag with the Encounter, `f_w` being the word's grammar factor, so `words × grammar` is what is paid; it is shown only when it is not 1.
- **Automation:** unlocks at region 2. The player chooses an interval from those owned (start 10 s; upgrades 5 s, 2 s, 1 s). Each tick buys one unit of the affordable Encounter with the lowest `cost / Δrate`. Decided in #33: Pemandu opens at the first destination of region 2 or later (`BALANCE.automation.opensAtRegion`), or one destination earlier with the stamp upgrade, judged on the destination reached, so a Mastery replay never closes it. Its ticks are the multiples of the interval on the simulated clock, and `integrate` takes every tick in `(anchor, new sim]`, so the tick at an action's own millisecond comes before the action (`apply` advances first) and a new setting's first tick falls after it. A tick buys at most one unit, through `buyEncounter`, so it pays the stamp discount as a purchase by hand does. The candidates are the Encounters of the regions reached whose next unit the Understanding held pays for; `Δrate` is that Encounter's rate with one more less its rate now, every multiplier included, so a unit reaching a milestone gains the doubling of its kind; `cost / Δrate` is compared by cross-multiplying, so no gain is divided by; a tie goes to the lower id in code-unit order. The next purchase tick is solved in each segment (an hour bucket, cut at a held festival card's edges) from its constant rate, then confirmed at that tick and the one before.
- **Set Sail goal:** destination `i` (0-based over all 12) needs `U_goal(i)` and `words(i) = w₀ + w_step · i`. **Mastery mode** replays a destination with its goal × `1.5^replays`. Amended in #35: `U_goal(i)` is `BALANCE.sail.goals[i]`, one value per destination tuned by the pacing bots, and a destination beyond the table is a `RangeError` naming it. The first design, `U₀ · g_U^i`, cannot meet §6's targets: one run's Understanding climbs about 10⁴-fold in its first hour and only about 14-fold over the next eight days (measured 2026-10-03), so a 45-minute first destination and 2-day later ones need a first goal about 10⁴ below the second, and each region's first destination a step about 10³ above the one before it, where that region's Encounters arrive.
- **Set Sail (#31):** destinations are numbered region by region in course order, and `i` is that number. `U_run` is the Understanding **earned** this run: what is held now plus what this run has spent on Encounters and pick-ups, the starting grant included, so buying never moves Set Sail further away. `words(i)` counts the held items of the current destination's own lexicon, so a Mastery replay, whose words are already picked up, still meets it, and only `U_goal` scales. Sailing pays `floor(k · sqrt(U_run / goal))` stamps, adding to both the stamps held and those ever earned, sets Encounters to none and Understanding to the starting grant, and changes nothing else: Journeys still out keep running and bring back the card they drew. Before the finale a sail goes to the next destination, and is refused when that destination lies in a region outside the playable ones `initialState` was given (default 3) or the course has no next destination. Sailing from the course's last destination sets the finale flag, and that sail and every later one names a visited destination to replay, whose `replays` count rises by one. The pick-up pool and the Journey card pool follow the current destination and its region. Encounters can be bought from every region reached so far (operator, 2026-10-03), and one from a later region is refused.
- **Unfold (#31):** `unfold(course, state)` derives parent §4.1's flags in that order from state alone, each from evidence that never goes away, so a flag never turns off: `listen` always; `encounters` once `U_run` reaches the first Encounter's threshold or the player has sailed; `words` once a word is held; `review` once a held word is due or has been reviewed; `upgrades` once there is Insight, an upgrade level or a stamp earned (D1); `journeys` with `review` (operator, 2026-10-03); `culture` once a card is held or a Journey has returned; `goal` with `culture`, or once the run's goal is met or the player has sailed (operator, 2026-10-03), so a goal is never hidden while it can be met.
- **Seasonal bonus:** while a festival's wall-clock window is live, its card's bonus is ×2. Windows come from `CourseData`, so moving festivals are content, not code.
- **Journeys (#30):** durations `tutorial` (30 min, once per game), `2h`, `4h`, `8h` and `24h`, each cut by the stamp upgrade and rounded to whole milliseconds when the Journey starts, so its return time is fixed then. Slots are numbered from 0; one beyond those open is refused, and so is one holding a Journey, returned or not. The card is drawn when the Journey starts, uniformly over the current region's cards in course order from the `cards` stream, with replacement (operator, 2026-10-03). A return changes no stored quantity: a Journey has returned once `sim ≥ returnsAt`, so the return falls at the same simulated time however `integrate` is split, and `advance`'s summary counts the returns in the time it credited. Collecting credits the card at that moment. A card not yet held joins the held cards: its phrase pack joins the pick-up pool and its bonus applies from then on. A held card pays a repeat reward instead, Insight by duration plus Understanding equal to the rate at collection times that duration's reward time; both tables are in `balance.ts`, and nothing is measured yet.
- **Card bonuses:** an Encounter's `cards` line is `1 + Σ bonus` over the held cards sharing one of its tags, each bonus ×2 while its festival window is live at wall time; its `sets` line is `1 + Σ bonus` over the complete sets. Each line shows only when it applies, like a Phrasebook's, and both sit before `stamps`. A festival edge falls inside an hour bucket at a fixed simulated time (the skew changes only at an anchor), so production splits there and the rate changes exactly at the edge.
- **Phrase packs:** the pick-up pool is the current destination's lexicon followed by the packs of the held cards in course order, put in curriculum order; a pick-up's `n` counts the items of that pool already picked up.

## 6. Pacing bots

- **Personas.** _Idler_ opens twice a day for 2 minutes and never reviews. _Casual Learner_ opens 3 times for 5 minutes and answers every due review. _Diligent Learner_ opens 5 times for 8 minutes and answers every due review. A _Clicker_ (Casual plus Listen at 10 taps a second throughout each open) exists only for the DN10 check; it shares the Casual Learner's seed, and each persona draws recall, latency and open times from separate RNG streams, so the only difference between the two runs is the clicking. A _Casual Non-learner_ (the Casual Learner's opens and seed, never reviewing) exists only for the D1 check in the same way. Every persona starts with one 60-minute first session.
- **Open times** are seeded per persona around waking hours (08:00–22:00 on the simulated wall clock), so the run is reproducible. Amended in #35: waking hours are split into one equal slot per open and each open falls in its own slot at least an hour before the next slot starts, so two opens are never closer than an hour. Drawn independently, opens landed minutes apart or overlapped (measured 2026-10-04: of the Diligent Learner's six opens without a decision, three began before the open before them had ended and two within 2.1 minutes of its end), which no player would call two visits.
- **Recall model.** A due review is answered correctly with probability equal to the word's FSRS retrievability at that moment, drawn from the persona's seeded RNG. Latency is drawn from a log-normal centred on 2.5 s.
- **Policy** at each open: answer the queue (learners only); collect and restart journeys with the longest duration that returns before the next scheduled open; buy greedily by payback; pick up words when the next pick-up's payback is shorter than the best Encounter's; buy upgrades and grammar nodes when affordable, in a fixed priority order; Set Sail as soon as it is available. Amended in #35, because the buying style decides the pace more than any constant does (measured 2026-10-03 on one balance: at most 5 purchases per 2-minute pass left the Casual Learner short of the finale after 70 days, buying everything affordable by payback finished it in 3.1 days): "greedily" means one unit at a time, by `price / gain` from `view`, until nothing is affordable; with nothing owned, the bot taps Listen until the cheapest Encounter is affordable, as a person would after every sail; and an open checks every 30 s of simulated time, so a sail lands within 30 s of becoming available rather than on a coarser grid (a 2-minute grid alone moved the first sail by 4%, most of assertion 7's 5% margin). Times are measured from the first open, 08:00 UTC on 2027-01-04; the game is created at the epoch, 00:00, which credits nothing since nothing is owned.
- **Less-efficient buyers (#35, operator 2026-10-03: report only).** Two more personas keep the Casual Learner's opens, reviews and seed and differ only in how they buy: the _Capped Buyer_ picks by payback but makes at most 5 purchases per 2-minute check, and the _Random Buyer_ buys while anything is affordable, choosing uniformly among the affordable Encounters and the next pick-up from its own seeded stream. No assertion reads them; the report shows how wide the range of play styles is.
- **The bots read `view` (#35 AC3).** `view` gains `shop`, every offer a UI shows: the Encounters of the regions reached (owned, price of one, the rate one more adds, affordable), the next pick-up (cost, the rate it adds, affordable), the upgrade catalogue (currency, level, next cost, affordable), the course's grammar nodes not yet owned (cost, affordable), the Journey slots (status) and the durations that can start, and Pemandu (opened, enabled, interval, owned intervals). Each `affordable` is whether the real action would be accepted at that moment, so the shop can never disagree with `apply`.
- **The course** is `fixtures/synthetic-course.ts`, generated from a seed and sized like v1 (parent §5.6): per region 150 lexicon items, 12 culture cards in sets, 6 Encounters, 4 grammar nodes, and about 10 tags. It satisfies the same `CourseData` type that M2's real content must. Amended in #35 (operator, 2026-10-04): an Encounter's price and output are not content. `CourseData`'s Encounter carries a `tier` from 1 to 6 in place of `c0` and `p0`, and `balance.ts` holds the ladder by tier and each region's step, so every course, synthetic or real, plays on the ladder the bots tuned, and the real-content runs (#121, #243) check what content does change: words, tags, cards and destinations.
- **CI assertions** (one test each; each mutation-verified by mistuning `balance.ts`):
  1. first Set Sail in **30–60 min** for every persona;
  2. each later destination in **1–3 days** for the Casual Learner;
  3. the Mudik finale in **3–5 weeks** for the Casual Learner;
  4. the Idler reaches the finale within **10 weeks** (my number: the parent says only "can finish");
  5. every open of every persona offers at least one meaningful decision (DN1): an affordable purchase, a due review, a free or returned journey slot, or an available Set Sail. So does a return 15 minutes after each open ends, judged on a copy of the state, so the personas' one-hour gap between opens is not what makes this pass (operator, 2026-10-04: _"there should be always something to do"_; sooner than that, Practice mode is on offer, parent §3.4);
  6. learning pays (D1): the Casual Learner reaches the finale at least **20%** sooner than the Casual Non-learner (my number for the parent's "large multipliers"), and Diligent ≤ Casual ≤ Idler in time to the finale;
  7. clicking never beats idling: the Clicker's time to each Set Sail is at least 95% of the Casual Learner's (DN10);
  8. no state on any persona's path contains NaN, a negative or an infinite value.
- **Report.** Each run writes `pacing-report.json` (per persona: every Set Sail time, finale time, first Mastered word day, opens without a decision) and CI uploads it, so balance changes are reviewed as numbers. The first Mastered word day is the measurement the parent §10.1 asks for.

## 7. Testing

- **Unit and property tests** (Vitest + fast-check), written first:
  - `integrate(integrate(s, a), b)` **deep-equals** `integrate(s, a + b)` for generated states and integer gaps: bit-exact, no tolerance (§2.2);
  - `apply` then `advance` equals `advance` then `apply` when the event's `wallMs` is the later time, while the gap stays within the offline cap: when the cap clips, advancing first banks the cap at the earlier time and then credits the rest, so the two differ by design and the live state never stores an `advance` (#34);
  - no NaN, negative or infinite value in any reachable state;
  - FSRS rank transitions, the floor, and queue order and cap;
  - the closed-form mean R agrees to 1e-12 relative with a reference table computed at 30 significant digits, over 5 stabilities × 6 spans × 5 window starts (#28 AC3; quadrature cannot reach that precision near `T` = 0);
  - the bulk-buy closed form equals summing single purchases;
  - every rejection fires and leaves state unchanged.
- **Cross-engine determinism:** a golden event log (a seeded 5-week Diligent run) is replayed in Node and, through Playwright, in **Chromium, WebKit and Firefox**; all four must produce the same `stateHash`. This test turns §2.1's one-off measurement into a guard. Amended in #34: the golden log is a committed fixture, `packages/core/fixtures/golden-log.jsonl`, written by `npm run golden-log` from a seeded 5-week Diligent-style policy (§6's opens; every due review answered, correct with the word's retrievability; journeys, upgrades in catalogue order, grammar, Pemandu at its fastest owned interval and Set Sail as soon as each is available) that also sends one refused event per open (a stale `seq`, a review not due, an unknown Encounter and the like), and moves the device clock back once a day. Its header records the live state's hash; replaying it must reproduce that hash in Node and in each browser, so any change to a rule or a dependency that moves a bit regenerates the fixture deliberately. Replaying it takes about 4.4 s of Node CPU (measured 2026-10-03).
- **Source guards** (comments stripped, mutation-verified with the comment left in place): the banned-API rules of §2.1 and §3.
- **Stryker** mutation testing over `encounters`, `words`, `memory`, `production`, `sail`, `journeys`, `upgrades`, `grammar` and `automation`, run in CI with `break` at 90%.
- **Offline returns** at 1 h, 1 day and 30 days (DN19): the 30-day return is capped, ages memory by the full 30 days (§2.3), is summarised, and finishes in under 1,000 ms on the CI runner. The measured time goes in the pacing report, so a slowdown is visible long before it fails.
